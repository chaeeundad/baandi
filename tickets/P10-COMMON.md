# Common rules for the P10 tickets (read first)
Context: AGENTS.md (read order, hard rules, generality rule, performance work, output formats, QE source policy), docs/performance/README.md and optimization-log.md (what was measured and rejected: do NOT repeat rejected experiments without a new, testable hypothesis), docs/decisions/*, ownership.toml, the current code. The repository state is live: inspect it first (git log, `git worktree list`, tickets/, artifacts/sessions.json, the docs listed in your ticket) and do not duplicate work that exists; if part of your task is already implemented or actively assigned, narrow your task and say so in the report.
1. Generality: BAANDI is a general-purpose plane-wave DFT engine. Validate on several different systems, not on silicon only (AGENTS.md "Generality rule"): synthetic Hermitian operators, the synthetic pseudopotential fixtures in the repository tests (varied valence, projector counts, cell shapes, band counts) and the real Si validation case. The Si validation UPF is /Users/mino/Develop/rust-dft-wt/pseudo/Si.pz-vbc.UPF (read-only; never copy, commit or send it anywhere).
2. Numerical correctness first: keep every existing gate (scripts/check.sh, ignored release tests, QE comparison scripts); no tolerance is relaxed; default behavior stays unchanged unless the ticket says otherwise; report eigenvalues, residuals, orthogonality, charge conservation and total energy; distinguish numerical convergence from physical correctness. Existing verified numbers: docs/validation.md; performance baselines: docs/performance/baseline-after-o2.json (bit-identity) and the logs.
3. Performance claims need reproducible evidence: release builds, hardware, compiler and library versions, thread counts, repeated runs with variability, complete SCF or Hamiltonian timings and not isolated kernels only, separation of algorithmic from implementation effects. The Mac is shared (other jobs run): Claude re-measures on the quiet dev08 node (2 x Xeon Gold 6230, MKL 2026.1 at /opt/intel/oneapi/mkl/2026.1) through the dft5090 session; say what you need measured there.
4. Implementation: stay inside the OWNED_FILES of your ticket; no new dependency without the ADR/approval path (license, maintenance, Apple Silicon); no unsafe outside the FFI adapter crate; CPU-only functionality is preserved; no mandatory CUDA/MKL requirement; explicit ownership of buffers; no allocation in hot loops; deterministic results for every thread count (see P7P6/P7PA/P7PB).
5. Workflow: you work in your own git worktree on branch task/<TASK>; the sandbox cannot write git metadata: leave all changes uncommitted and say so; Claude commits, pushes the branch, opens the pull request (public development) with your report as the description, reviews it and merges after verification. Document significant decisions as ADRs (docs/decisions/, next free number: check) and explain rejected approaches in the log.
6. Report format: docs/schemas/report.schema.json, real exit codes only; list for every acceptance criterion the evidence. Work step by step and finish the whole ticket in one run; stop only when done or truly blocked (name the missing file or permission).
