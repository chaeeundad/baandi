TASK_ID: P7E-EXPR
GOAL: Let numeric inputs be written as arithmetic expressions, for example "1/4", "2+1/3", "atan(0.5*pi)", "sqrt(3)/4", "5.43/2 Angstrom", "0.5*30 Ry". This ticket delivers the evaluator and its unit-aware quantity parser in dft-units only; wiring into dft-cli TOML is a later ticket (P7E2) after P7A2 is merged, because P7A2 owns dft-cli right now. Use a general-purpose library: exmex 0.21 (MIT OR Apache-2.0; no default features) is already in the workspace manifest, vendored and referenced by crates/dft-units/Cargo.toml. evalexpr is rejected (AGPL-3.0), do not use it. Hand-written expression parsing is not allowed.
OWNED_FILES: crates/dft-units/** (a new module `expr`, tests, additive API), docs/decisions/0014-expression-inputs.md (create), docs/dependencies.md (add exmex: version from Cargo.lock, license, consumer dft-units, features off, its transitive crates regex, regex-automata, regex-syntax, aho-corasick, memchr, smallvec with licenses from `cargo metadata`; say which were already present), docs/physics-conventions.md (append a short section on expression inputs), scripts/tests/ (extend test_no_hardcoded_units.py only if needed so it still passes). Do not touch the workspace Cargo.toml, Cargo.lock, other crates, AGENTS.md, ownership.toml, tickets/, artifacts/, or the existing dft-units public API behavior (additive only).
READ_ONLY_CONTEXT: AGENTS.md, crates/dft-units (current API, parser for "30 Ry" strings, errors), docs/decisions/0003, 0012, the vendored exmex source (how to supply constants such as pi: exmex treats an unknown name as a variable, so the wrapper must bind named constants through its variable mechanism, taking the values from std::f64::consts, never typed digits).
DESIGN REQUIREMENTS (record in ADR 0014):
1. API in dft-units: `eval_expr(&str) -> Result<f64, ExprError>`; `parse_quantity_expr(&str, QuantityKind) -> Result<..>` or the same shape as the existing "30 Ry" parser, extended so the numeric part may be an expression and the unit is the final whitespace-separated token (state the rule precisely: unit token = trailing alphabetic or slash/caret token after the last whitespace; an expression can contain spaces and parentheses; "2 * 5.43 Angstrom" works; "30 Ry" and "30Ry" keep working exactly as before). A plain number must behave exactly as before.
2. Closed vocabulary, documented: operators + - * / ^ and unary minus, parentheses, constants pi and e (from std::f64::consts), functions sqrt, abs, sin, cos, tan, asin, acos, atan, exp, ln, log10 (restrict to what exmex provides; remove anything that would be locale or implementation dependent; state the list). No user variables, no assignment, no function not in the list.
3. Strictness: result must be finite (reject inf and NaN, including 1/0 and sqrt(-1) and asin(2)); empty, trailing operator, unknown name, unknown function, and a leftover variable are typed errors that quote the offending text; the error type is documented and non-exhaustive-friendly.
4. Determinism and reproducibility: the evaluated f64 is what the engine uses; provide a function that returns the resolved number so that the CLI can record "expression text -> value" in results.json later (document the intent, implement just the data type).
5. Integer helper: `eval_expr_integer` for inputs such as grid sizes that must resolve to an exact integer within 1e-12 relative, otherwise an error (so "8/2" works and "7/2" is rejected).
TESTS (stated tolerances, printed values): 1/4 = 0.25 exactly; 2+1/3 equals 2.0 + 1.0/3.0 bit-for-bit; atan(0.5*pi) equals f64::atan(0.5*std::f64::consts::PI) within 1 ulp; sqrt(3)/4; precedence and associativity (2^3^2 follows the documented exmex rule: state it from a test, do not assume; -2^2); whitespace variants; all error cases above; every function against std at a few points within 1 ulp; quantity forms "5.43/2 Angstrom" = 2.715 Angstrom and "0.5*30 Ry" = 15 Ry = 7.5 Ha through the existing conversion; legacy strings unchanged; the hardcode guard still passes; a test that no digits of pi or e are typed in dft-units source. scripts/check.sh green; python3 -I -m unittest discover -s scripts/tests green.
ACCEPTANCE_CRITERIA: all tests pass with real numbers in the report; no hand-written parser; no typed math constants; ADR 0014 and docs updated; legacy behavior unchanged.
NON_GOALS: CLI/TOML wiring (P7E2), variables or user functions, symbolic math, units inside the expression beyond the one trailing unit.
DEPENDENCIES: P7U merged (done). Runs in parallel with P7A2 (dft-cli); do not touch dft-cli.
GIT: Leave changes uncommitted and say so.
RETURN_FORMAT: docs/schemas/report.schema.json. Real exit codes only.
