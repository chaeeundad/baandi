TASK_ID: P9B-PSEUDO-REGISTRY
GOAL: A pseudopotential registry and download workflow so that users can obtain pseudopotentials from public repositories instead of supplying files by hand, safely: every file is identified by element, source, version, license and SHA-256; the engine tells whether it can use the file (its UPF reader and physics have limits: norm-conserving UPF v2 subset, at most three projectors per channel today, no nonlinear core correction, no spin-orbit, no PAW/USPP); downloads are initiated by the user, verified against the registry, cached outside the repository, and never committed (AGENTS.md: never commit UPF files). The user's words (Korean, paraphrased): it would be good to add a feature to download pseudopotentials from public repositories.

Commun. 196, 36 (2015)) is hosted at quantum-simulation.org and is licensed CC BY-SA 4.0 (v1.0 and v1.2 UPF, tarball dated 2020-02-06 mentioned in the ecosystem); SSSP libraries (Prandini et al., npj Comput. Mater. 2018) on Materials Cloud are licensed CC BY 4.0 as a collection of pseudopotentials from different authors who must be acknowledged, with efficiency and precision variants and recommended cutoffs; the PseudoDojo (van Setten et al., Comput. Other candidate sources to evaluate: pslibrary and GBRV (ultrasoft/PAW, unsupported by the engine today but should be listed as "not usable"), Hamann's ONCVPSP outputs, the Materials Cloud SSSP verification data (recommended cutoffs per element).

DESIGN REQUIREMENTS:
1. Registry entry fields: id, element, source (family, version, URL of the file, URL of the project page), license (SPDX id or text pointer), attribution text and required citations, formats, XC functional, valence electrons, relativistic treatment, NLCC flag, spin-orbit flag, projector counts per channel, suggested cutoffs if the source gives them (with the source), SHA-256 of the exact file, size, date checked, `supported_by_engine` (computed, with the reasons when false), status (verified / unverified / deprecated). The registry is data in the repository (metadata only); UPF files are never in the repository.
2. Offline subcommands (implement now): `dft-cli pseudo list [--element X] [--supported]`, `pseudo show <id>` (full metadata, license and the citation text, plus the project page link), `pseudo verify <file>` (compute SHA-256 and compare with the registry, report which entry it is, or that it is unknown), `pseudo path` (the cache directory: environment variable `BAANDI_PSEUDO_DIR` or the platform cache dir, documented), `pseudo suggest <composition or elements>` (for each element the supported registry entries ranked by a documented rule, the suggested cutoff and the reason; if no supported entry exists say which engine capability is missing, for example "transition-metal pseudopotentials in this registry need nonlinear core correction, which the engine does not support yet"; never silently pick an unsupported file).
3. Download workflow DESIGN (document it; implement the offline parts and a pluggable fetch step with the network call behind a clearly marked interface that is NOT implemented here, because the HTTP client policy is being decided by ticket P9A): `pseudo fetch <id>` writes into the cache directory, verifies SHA-256 BEFORE accepting the file (a mismatch deletes the download and fails), prints the license and the attribution/citation text, requires an explicit `--yes` or interactive confirmation before any network access, records provenance (id, URL, date, hash) in a small manifest next to the file, never overwrites an existing different file, works offline with `--offline` using the cache only, and treats redirects and TLS errors as failures. Also design how the input finds its pseudopotentials: `[pseudopotentials] Si = "registry:sg15-si-v1.2"` or a plain path; the preflight (ticket P8G) checks identity and support.
4. Legal and safety design: what the project may store (metadata and hashes only), attribution and ShareAlike implications (we neither redistribute nor modify the files; the user downloads from the original site; state this), the license of each source family recorded and displayed, what to do when a source license is unverified (do not auto-download; require the user to read the source page), and a note on the unverified provenance of the validation Si.pz-vbc.UPF used so far (docs/candidate-si-upf.md): recommend replacing it by a registry entry once a verifiable Si norm-conserving LDA file is available.
5. Engine compatibility matrix: for the main families (SG15, PseudoDojo, SSSP members) which elements the current engine could use (NC UPF v2, three projectors per channel, no NLCC, no SOC) and which need which capability; compute it with the builder script where files are reachable, otherwise document as unverified. Tie the missing capabilities to the roadmap (docs/research/xc-and-manybody-roadmap.md from ticket P8D and the feature-gap survey if present).
TESTS: schema validation of the registry and of deliberately broken registries; the checker's consistency rule; `pseudo list/show/verify/path/suggest` outputs (use synthetic registry fixtures and synthetic UPF fixtures from the repository; never a real UPF file in the tests); `verify` for a matching, a mismatching and an unknown file; the suggestion refuses unsupported entries with the capability message; the cache-directory resolution rules; scripts/check.sh and python3 -I -m unittest discover -s scripts/tests green.
ACCEPTANCE_CRITERIA: offline workflow implemented and tested; registry schema and checker; the initial registry contains no unverified hash presented as verified; documentation for non-programmers; the fetch design documented with the network step isolated; no new dependency; no unsafe.
NON_GOALS: the network client itself (decided by P9A), PAW/USPP support, pseudopotential generation, bundling any pseudopotential.
GIT: Leave changes uncommitted and say so.
