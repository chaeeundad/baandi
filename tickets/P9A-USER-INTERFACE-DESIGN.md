TASK_ID: P9A-USER-INTERFACE-DESIGN
GOAL: Design (no feature code) the user-facing interface of this engine so that a researcher can start calculations without learning a private tag language: standard structure formats, the input formats of the established codes, near-natural-language requests, structures fetched from the Materials Project (and similar open databases) with explicit disambiguation, a conversational/guided CLI, and link-based result viewing. The user's words (Korean, paraphrased): QE and VASP force users to write their own tags and structure formats; this engine should accept standard formats and other codes' inputs, and almost natural language; with a Materials Project API key it should fetch a structure and run it; typing a formula such as Fe3O4 should search the database and make the CLI ask which Fe3O4 is meant (with web links); link-based work in the CLI is fashionable, so result visualization should also be possible conversationally from the CLI.
OWNED_FILES: docs/architecture/user-interface.md (NEW), docs/roadmap/ui.md (NEW), docs/research/ui-landscape.md (NEW). Nothing else. Web research is allowed and required for ecosystem facts (cite title, year, URL, access date; no copied text); you must NOT read, clone or reproduce any Quantum ESPRESSO or other GPL/proprietary source; VASP and others only through their public documentation.
READ_ONLY_CONTEXT: AGENTS.md (output formats policy, reporting rules), docs/architecture.md, docs/cli.md, docs/decisions/0017 (coupling commitments: adapters stay outside the core), 0012 to 0015 (units, expressions, k-point input), docs/research/feature-gap-survey.md (verified gaps, including the species/pseudopotential identity problem), docs/roadmap/*.md, crates/dft-cli/src, examples/, tickets/P8A-BANDS-DOS.md and tickets/P8B-VOLUMETRIC.md (output formats in progress).
REQUIRED CONTENT:
1. Layered architecture with ownership (which crate or adapter, what stays out of the numerical core): L0 the existing TOML input; L1 structure and input importers (POSCAR/CONTCAR, CIF, XYZ/extxyz, XSF, QE pw.x input, VASP INCAR + KPOINTS, ASE/pymatgen JSON; note that POTCAR is licensed and must not be read or redistributed) with a TRANSLATION REPORT for every import that lists what was mapped, what was defaulted, what was ignored and what is unsupported (never silently dropped); L2 "recipes" and a deterministic near-natural-language request grammar (examples in English and Korean such as "relax Fe3O4 mp-19306 with PBE at a 4x4x4 mesh", "band structure of silicon along the standard path", "show the density") that compiles to an explicit, printable, editable input file; L3 conversational/guided mode (REPL or wizard); L4 an agent-facing interface (machine-readable capability description, JSON schema of inputs and results, an MCP or similar tool server so that coding agents and chat assistants can drive the engine) because the natural-language layer should not be reinvented inside the engine; L5 result viewers.
2. Materials Project integration: verify the CURRENT API (base URL, authentication with the API key header, the summary/materials endpoints and fields that matter: formula, material id, space group, energy above hull, formation energy, band gap, magnetic ordering, volume, number of sites, calculation type, structure; versioning and rate limits; the data license and the attribution/citation requirements; terms of use for the key), how to search by formula (and chemical system and element lists), how to rank and present candidates (stability, ground-state flag, space group symbol, number of sites, energy above hull, link to the web page https://next-gen.materialsproject.org/materials/<id> or the current equivalent), the disambiguation dialogue flow, key handling (environment variable or a config file with restricted permissions; never printed, logged, committed or put into result files), caching and offline mode, reproducibility record (material id, database release, query date, structure hash) stored in the results, behavior without a key or without network, and test strategy without network (recorded fixtures). Also compare with other open structure sources (COD, OQMD, AFLOW, NOMAD, JARVIS, OPTIMADE as a common API: check whether OPTIMADE makes one adapter enough) and recommend an adapter design.
3. HTTP and dependency policy: how the network client is isolated (optional feature or a separate adapter crate; options: a pure-Rust HTTP client with TLS, a system `curl` call, or a small external helper), license/maintenance/Apple Silicon checks, and the principle that the numerical core never touches the network (ADR 0017).
4. Capability awareness: the interface must tell the truth about what the engine can do today (spin-unpolarized, norm-conserving, LDA/PBE, insulators): a request such as Fe3O4 with magnetism, +U or metals must produce a clear message listing the missing capabilities and the roadmap item, and must NOT silently run an inappropriate approximation (AGENTS.md and ESLE principles). Design the capability negotiation and the wording; include pseudopotential selection and identity verification (element check against the UPF header, a curated registry with hashes and licenses, no silent defaults), cutoff and k-mesh suggestions with the rule used, and how recommended settings are recorded.
5. Link-based CLI experience: terminal hyperlinks (OSC 8), what to print as clickable links (material page, results folder, HTML report), a self-contained offline HTML result report (structure view, bands, DOS, convergence, energy components; no external CDN at runtime, only inline assets; choose and justify the viewing technique and licenses of any embedded library), and an optional local viewer served on localhost with a printed link; conversational visualization ("show the density slice", "plot bands") as commands over the same outputs (standard formats first, per the output formats policy); screenshots or image export where feasible.
6. Safety and trust: key handling, confirmation before network access and before expensive runs (estimated cost shown), data provenance, reproducible request records, translation reports, deterministic compilation of natural language to an explicit input that the user can review.
7. A prioritized implementation roadmap with the first fifteen tickets (title, owned areas, gate, dependencies, estimated agent-days), the quick wins, what to build first for the largest user value (suggested order: importers + translation report, input preflight with species identity (ticket P8G), recipes, MP adapter, guided mode, agent/MCP interface, HTML report), and the decisions needed from the user (marked clearly; for example which databases and whether an LLM-backed natural-language mode is wanted inside the CLI or via the agent interface only).
8. Limits of this document: what you could not verify, what is opinion.
OUTPUT: English Markdown, summary table at the top of each document, references at the end.
ACCEPTANCE_CRITERIA: all items covered; ecosystem facts verified with sources and dates (state when not verifiable); consistent with ADR 0017 and the output formats policy; no repository changes other than the three documents.
GIT: Leave the new files uncommitted and say so.
