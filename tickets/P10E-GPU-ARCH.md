TASK_ID: P10E-GPU-ARCH
GOAL: A GPU execution architecture design (documents, with a feasibility analysis; a hardware prototype only if a machine is available: none is approved now, so the prototype part is skipped unless the report finds one already usable without installing anything) that fits this engine: modular, backend-neutral, CPU path preserved, no mandatory CUDA, Metal or other GPU dependency. The user also develops on Apple Silicon: treat NVIDIA (CUDA) and Apple (Metal) and portable APIs (wgpu/Vulkan, SYCL, ROCm/HIP) as candidates with an honest assessment. Read tickets/P10-COMMON.md, docs/decisions/0001, 0004, 0016, 0017, 0019, docs/research/electronic-state-landscape.md and docs/architecture/electronic-state.md (GPU-neutral state semantics), docs/architecture/scientific-coupling.md (backend-neutral contracts), crates/dft-numerics, dft-physics (Hamiltonian apply), dft-solvers (Davidson data flow), dft-engine (SCF controller, threading), docs/performance/*.
OWNED_FILES: docs/architecture/gpu-backend.md (NEW), docs/research/rust-gpu-ecosystem.md (NEW), docs/roadmap/gpu.md (NEW), docs/decisions (ADR proposal, next free number). Nothing else. Web research is allowed and expected (cite title, year, URL, access date; state when a fact could not be verified); no source code of other projects is read or copied.
CONTENT: (A) Verified inventory of the CPU data flow: where wavefunctions, densities, potentials and operator products live, which operations dominate (profile in docs/performance), which are GPU-suitable (3D FFT, GEMM, Gram matrices, orthonormalization, subspace diagonalization, nonlocal projections, density accumulation, local-potential multiply) and which stay on the host. (B) The abstraction: what a backend trait must cover (memory ownership for host and device, persistent device-resident wavefunction blocks and workspaces, FFT plans, GEMM and small dense eigenproblems, streams and synchronization, error propagation, determinism: how bit reproducibility relates to GPU reductions) and how it relates to the existing backend isolation (ADR 0001) and the optional MKL backend (ADR 0019) and the fused operator API that ticket P10C defines; the SCF controller and the physics layers must not see device types. (C) Transfer analysis with numbers: sizes of wavefunction blocks and density grids for target systems (from 8 to 500 atoms), PCIe and NVLink or unified-memory bandwidth, the break-even problem size below which a GPU is not worth it (the small Si cases are such), and the data that must stay resident. (D) Rust GPU ecosystem assessment: CUDA runtime and driver bindings, cuFFT and cuBLAS and cuSOLVER bindings, safe wrappers, memory management and asynchrony, Metal bindings for Apple Silicon (including the Accelerate/vDSP/Metal Performance Shaders options for FFT), wgpu compute, maintenance status, safety, Apple Silicon and Linux compatibility, licenses (the project is MIT; flag any copyleft or proprietary runtime), build and CI implications. (E) A staged roadmap with gates: single-GPU FFT, GPU Hamiltonian application, GPU linear algebra, GPU eigensolver, full GPU SCF, multi-GPU and MPI; each stage with its validation oracle (CPU reference to a stated tolerance; transfer-inclusive timing) and the hardware it needs; what to build first and what to defer; risks. (F) Which decisions need the user (a machine with an NVIDIA GPU, whether Apple Metal is a target, the build policy for proprietary SDKs).
GATES: documents complete with sources; claims about this repository verified in files; CPU-only builds remain untouched; no code changes.
DELIVERABLES: the three documents and an ADR proposal, report.
