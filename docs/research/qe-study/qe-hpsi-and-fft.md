## 1. What the QE 7.6 CPU path does for one block of bands (complex wavefunctions at a k point)

Facts about the call structure:
1. The solver calls the H application once per Davidson step on the contiguous block of NOT-yet-converged correction vectors (plus once on the whole starting block at the start of each solve). The block therefore has m = number of unconverged roots, which is also the shape of every matrix product below.
2. `h_psi` first forms the kinetic term as one multiplication of every coefficient by |k+G|^2 (stored per k in Rydberg units, computed once per k visit) and zeroes the padding beyond the true plane-wave count. Then the local part, then the nonlocal part, then optional extras (Hubbard, exact exchange, meta-GGA, fields; none apply to our scope).
3. The local part for k points is the same routine family as the GPU one (the "acc" file is the only implementation in 7.6). On CPU the batch size `many_fft` is 1 (the value 16 exists only in CUDA builds). The loop is therefore strictly band by band: copy the band's coefficients to a small buffer, zero the whole real-space array, scatter coefficients into it through a double indirection (position of k+G in the global G list, then the grid position of that G), inverse transform of the whole box, pointwise multiplication by the real potential on the smooth grid, forward transform of the whole box (scaled by 1/N inside the transform), gather through the same double indirection, add to the output. Work arrays are allocated once per call, not per band. There is NO batching of bands on the CPU path and no reuse of the potential across bands; the multiply is a separate full pass over the box.
4. The nonlocal part is three dense matrix products on the whole block, with the projector matrix `vkb` (plane waves by projectors, all atoms side by side, leading dimension equal to the padded plane-wave count) held for the current k: (a) projections = vkb^H times the block (nkb by m, one ZGEMM; a ZGEMV when m = 1); (b) for each atom, the small channel-coupling matrix times that atom's slice of the projections (a tiny ZGEMM per atom; the real coupling matrix is copied into a complex scratch each call, "simple but sub-optimal" in the authors' own words); (c) vkb times the coupled projections, accumulated into the output (one ZGEMM). The overlap-matrix routine `s_psi` is never called for norm-conserving data (the solver is told there is no overlap term), so S = 1 costs nothing.
5. `vkb` is regenerated for each k point at every visit of the band solver (that is once per SCF iteration per k), not stored across iterations. Its construction (`init_us_2`): per k, compute |k+G|, the real spherical harmonics for all needed lm, and for each atom TYPE the radial factor by interpolation in a pre-tabulated radial transform (uniform table step 0.01 in inverse Bohr, four-point Lagrange interpolation); the product of radial factor and harmonics is formed once per type; for each atom the structure factor is assembled from three precomputed one-dimensional phase tables (one per reciprocal axis, indexed by Miller index) multiplied together with the single k-dependent phase, then the factor (-i)^l. The radial transform table is built once per run, not per k. So the per-k cost is O(npw times nkb) with small constants; no quadrature and no trigonometric call per (atom, G) pair.
6. Preconditioner and diagonal: `g_psi` divides each correction by the smooth positive denominator already described in note 1 (it only touches the m unconverged vectors; 0.01 s in the si8 profile). The diagonal handed to it is built per k by `usnldiag` from the kinetic energy, the mean local potential and the diagonal of the nonlocal operator computed from `vkb` and the coupling matrices. Note 1 and ledger row A14 cover this; nothing new here except that it needs `vkb` at that moment, one more reason QE keeps `vkb` resident during the solve.

What the source shows about the FFT layer, per backend:
7. The dispatcher `invfft`/`fwfft` for the wave kind has three code paths: (i) a serial path when the band group has one process (our reference: one MPI process): a "3D FFT using sticks" routine fed two integer maps, one marking which (x,y) columns contain sticks (the wave sphere) and one marking which x planes are touched; (ii) the parallel path with sticks, transposes and pencil or slab decompositions (z sticks, then y on the active x columns, then x on whole planes, with all-to-all exchanges between); (iii) a "many" variant for several bands per call, parallel driver only, that is used with the GPU or OpenMP tasking.
8. Serial path with the FFTW3 wrapper really prunes: inverse = 1D z transforms on the active sticks only (one call per stick), then 1D y transforms for the active x columns (one call per column, each a batch over all z planes with the column stride), then ONE batched x call over all lines of the box; forward is the mirror image (x full, y on active columns, z on sticks) followed by the 1/N scaling pass. Plans are measured (FFTW_MEASURE), kept in a small round-robin cache of 20 entries keyed by the transform sizes, and applied with the "new array" execute call; FFTW threads are used only when OpenMP is compiled in.
9. Serial path with the MKL (DFTI) wrapper does NOT prune: the stick-based entry simply calls the plain full-box 3D transform (in place, single descriptor, forward scale 1/N, backward scale 1). The 2D plane routine of the DFTI wrapper also ignores its column mask. This is the code the relayed QE reference ran (build with MKL, one MPI process, one thread). It confirms the fastqe finding that the MKL build transforms the whole box for every band, twice per H application.
10. Descriptor and plan caching for the 1D z batches (DFTI): descriptors keyed by (length, number of transforms, distance, in-place flag), created lazily, up to 20 live, replaced round-robin; thread-private under OpenMP. In the parallel path z, y and x are all executed as batches of 1D transforms with explicit transposes between them, not as 2D/3D library calls.
11. Padding: `good_fft_dimension` returns the transform length itself except on IBM ESSL (power of two gets +1) and NEC SX; so on x86 builds the leading dimensions equal the transform lengths. QE does not pad against cache aliasing. `good_fft_order` accepts lengths whose prime factors are 2, 3, 5 only for the FFTW and "all other" cases (7 and 11 are allowed only on ESSL); the same rule as `smooth` in dft-basis.
12. Task groups (`vloc_psi_tg_*`): with several processes per band group QE gathers whole bands to groups of processes, FFTs several bands at once, and multiplies by the potential gathered the same way. This exists to keep many processes busy on one k point when bands are few; it has no counterpart need in BAANDI, whose workers each own a band end to end (this is the communication-free equivalent).

## 2. Smooth grid, dense grid and the exact minimal wavefunction box

QE sets two cutoffs on the reciprocal side: the dense sphere (charge density, `ecutrho`, default 4 times `ecutwfc`) and the smooth sphere used by the wavefunction FFT, always 4 times `ecutwfc`. When `ecutrho` exceeds 4 times `ecutwfc` ("double grid", needed for ultrasoft, PAW, in practice also when nonlinear core corrections are hard) the smooth box is smaller than the dense one and the local potential is Fourier-filtered to the smooth sphere before use; for norm-conserving data without such need QE uses one grid for both. The box dimensions per axis come from the largest Miller index inside the sphere (found by scanning), doubled plus one, then raised to the next 2-3-5-smooth length. For the wave personality the sphere handed in is the smooth sphere, independent of k; the (x,y) stick and column maps use the shifted wave sphere (radius of k+G).

Derivation of why 4 is exact, and what a still smaller box would cost. Let m be the largest Miller extent of the wavefunction sphere along one axis and K the largest extent of the potential (K up to 2m for a potential defined on the 4-times sphere). The product of potential and wavefunction has extent up to K+m; we need only the components inside the wavefunction sphere (extent m) after projection. A component at extent f in (m, K+m] aliases onto extent f - N, which lands inside [-m, m] unless f < N - m. No contamination of the needed components therefore requires N > K + 2m; with K = 2m this is N >= 4m+1, which is precisely the box built from the 4-times sphere. So (a) BAANDI's box is already the exact minimum for a potential band-limited to the density sphere, and QE has no smaller grid for norm-conserving, non-doublegrid runs; (b) the only way to shrink the box further is to truncate the potential to K < 2m: N = 2m+K+1; for K = m the box has 3m+1 points per axis (25 instead of 36 for si8: 3 times fewer points). That is an approximation of the Hamiltonian (error equal to the dropped Fourier components of V acting on the wavefunction sphere), not an equivalent transformation; it violates the 1e-12 Ha gate by many orders in general. QE itself accepts exactly this kind of filtering only down to K = 2m (the smooth sphere). See hypothesis 7.

Observation on axis order: because every axis of the box is sized from the same sphere, the active fraction of each axis in the first two passes is about one half on all three axes whatever the cell shape; the order of axes therefore changes the pruned flop count only through the rounding of lengths up to smooth numbers and through log N differences. No axis-order heuristic is worth implementing.

## 3. Accounting per H application (derived; labelled estimates)

Model case: the BAANDI benchmark Si8 Gamma (complex), box 36^3 = 46,656 points, 2,969 plane waves, 20 bands, and an assumed 32 projector columns (8 atoms times s plus three p channels; the exact count depends on the UPF and should be read from the run). Flop model: 5 N log2 N per 1D transform; a complex multiply-add counts 8.
- 1D transform of length 36: about 930 flops. Full 3D: 3 passes of 1,296 lines = 3.6 Mflop; two per band = 7.2 Mflop (this is what QE with MKL does).
- Pruned (estimate): the wave sphere has radius about 8.9 Miller units, so about 249 of 1,296 (x,y) columns are sticks (19 percent) and about 17 of 36 x columns are active (47 percent). Inverse: z on sticks 0.23, y on active columns 0.57, x full 1.21, total 2.0 Mflop; forward the same; pruned total about 4.0 Mflop, i.e. 55 percent of the full cost. The last (dense) pass cannot be pruned because all grid points are needed for the multiplication; it is 60 percent of the pruned flops.
- Potential multiplication 0.09 Mflop, kinetic 0.006 Mflop.
- Nonlocal: 2 products times 8 flops times 2,969 times 32 = 1.52 Mflop per band, the same in the matrix-product form and in BAANDI's loop form (flops are not the difference).
- Total per band: about 5.6 Mflop pruned, 8.8 Mflop in the QE/MKL form.
- Bytes (estimate): projector matrix 2,969 x 32 x 16 B = 1.52 MB; an unblocked per-band application streams it twice (projection pass and accumulation pass), 3.04 MB per band; processing b bands per pass divides this by b. The wave box in the pruned scheme never exceeds the stick buffer (about 143 KB) plus one plane buffer (about 20 KB) plus the potential array read once (373 KB) plus coefficient vectors in and out (about 100 KB): about 0.7 to 1 MB per band, 2 to 3 GB/s at 0.3 ms per band, far below the sustained L2/L3 bandwidth. The FFT part is therefore compute-bound (consistent with ledger A28 and the fastqe report: grouping bands to reuse the potential does not pay). The nonlocal part is the opposite: arithmetic intensity 0.5 flop/byte on a streamed 1.5 MB matrix.
- Cache fit: the 1.52 MB matrix does not fit the 1 MB private L2 of the dev08 Xeon Gold 6230 but does fit the large L2 of Apple Silicon. This matches the opposite outcomes of the same traversal experiment on the two machines (A43: Mac neutral to positive, dev08 about 2 times slower function time) and is consistent with the dependence of the nonlocal function on L3 streaming; it is a hypothesis consistent with records, not a proof.

QE side, derived from the relayed si8 profile (conv_thr 1e-8, one process; complex Gamma, 20 bands, same box): wave FFT 0.29 s over 2,138 calls = 136 microseconds per full 36^3 transform (about 26 Gflop/s on the full count, a good fraction of one core's peak). The wave transforms count two per vloc band plus one per band in the density sum; with 14 band-solver calls and 16 to 20 bands per density sum this leaves about 1,850 to 1,900 vloc transforms, i.e. about 950 band applications (estimate; the profile gives 98 H blocks and 83 Davidson steps, so about 9.7 vectors per block on average, 280 of them the starting blocks). Then: vloc 0.32 s / 950 = about 0.34 ms per band; calbec plus add_vuspsi 0.04 s / 950 = about 42 microseconds per band (1.5 Mflop in 42 microseconds is about 36 Gflop/s: compute-bound GEMM); whole h_psi about 0.38 ms per band.

BAANDI side (relayed dev08 and ledger; counts of vectors differ between builds, hence ranges): 290 Davidson steps and 2,070 H vectors for si8 at T=1 (7.1 vectors per step) against about 950 for QE. Percentages from the MKL T=1 profile: FFT 10 to 15 percent and NonlocalOperator::add 12 to 15 percent of 4.8 to 6.0 s. Per vector: FFT 0.25 to 0.45 ms (in the MKL build the local part is the full-grid adapter around the same MKL 3D transform QE uses, so parity with QE's 0.31 to 0.34 ms is expected and observed to within the uncertainty); NonlocalOperator::add about 0.2 ms (the fe0492b function time of 0.474 s over about 2,100 vectors is 0.22 ms), which is about five times QE's 42 microseconds. Total per vector about 0.5 to 0.65 ms against QE's 0.38 ms: a factor 1.3 to 1.7 per vector, of which the nonlocal term is most.

Consequence for the framing of the gap (important): the H application is not where the per-Davidson-step time goes. Per Davidson step QE spends 3.7 ms in h_psi for about 9.7 vectors; BAANDI applies about 7 vectors per step at about 0.5 to 0.65 ms, i.e. about 3.5 to 4.5 ms, which is the same order. BAANDI's 17 to 20 ms per step is dominated by the algebra around the H application (note 4, ledger A35 to A55), and the total H time gap (about 1.2 to 1.6 s against 0.36 s) is made of two factors, vector count (about 2.2 times) and cost per vector (1.3 to 1.7 times). The hypotheses below can remove most of the second factor and, only in a build with a vendor pruned FFT, go below QE per vector; they do not change the first factor, which belongs to the solver notes.

## 4. What QE does better, what it does not do, and what BAANDI already has

QE better (for this scope):
- The nonlocal part as block matrix products reuses the projector matrix across all unconverged bands and runs at GEMM efficiency (about 5 times less time per band than our streaming loops on dev08).
- Radial projector transforms by table lookup: the per-k construction of the projector matrix costs O(npw times nkb) and the radial table is built once per run. BAANDI computes each radial transform by quadrature over the radial mesh for every (G, projector) pair at construction of each k's operator; this is one-time setup per k, and is likely small next to the SCF, but it grows with the number of k points and the mesh length. Unmeasured; see hypothesis 6.
- Using the vendor FFT through one descriptor per grid shape for the whole run (no per-call planning); BAANDI with MKL does the same through its own adapter.

QE does NOT do (so there is nothing to copy): batching of bands on CPU (many_fft is 1), reuse of V across bands, padding of FFT dimensions against cache conflicts, pruning when MKL is the backend, a smaller wavefunction grid for norm-conserving data (the smooth box equals the exact minimum), overlap applications for norm-conserving data, caching of `vkb` across SCF iterations, real-space tricks for the local term in the default path (the real-space beta option exists but is off by default and is a different algorithm).

BAANDI already has what the fastqe report and the FFTW wrapper achieve: pruned lanes and planes, no full-box zero fill, fused multiply, pure Rust (OrderedFusedPlan). Points seen in our code (read for this note, not profiled): (a) the ordered plan preserves historical rounding by scaling each inverse lane by 1/n and later multiplying by the box size, which is two extra complex-by-real passes per application (about 0.1 Mflop, below 2 percent of the work; kept for bit-identity, not worth changing alone); (b) every one-dimensional transform goes through a gather of the lane into a contiguous buffer, the transform, and a scatter back: about 3,800 lane operations per band for 36^3 (612 + 1,296 + 1,296 + 612 + stick passes); at about 36 complex moves each direction this is of the order of 10^5 element moves per band, which can be comparable to the transform arithmetic on a CPU where strided access is costly; the Mac experiment (A11, four-lane staging) found 1 to 4 percent, and dev08 was never run; (c) the projection pass in NonlocalOperator::add is a sequential floating-point reduction (a plain sum in coefficient order), which the compiler may not reassociate, so it executes as one dependent addition chain per component (latency-bound: about 3 to 4 cycles per complex term, which for 2,969 x 32 terms is about 100 to 130 microseconds at 3 GHz; estimate), and then the accumulation pass streams the matrix a second time; (d) the repository has no release-profile settings and no target CPU flags (no profile section in the manifests, no cargo config); on x86 the code is therefore compiled for the baseline instruction set (128-bit vectors) except where libraries dispatch at run time (rustfft, faer); the hand-written loops in dft-physics (nonlocal, kinetic, density) cannot use AVX2 or AVX-512 on dev08 unless the build there passes flags, which the relayed provenance does not record (question for the orchestrator).

## 5. Mapping onto BAANDI modules (where each idea lands)

- `dft-physics` `NonlocalOperator::add` / `apply_into` and `Hamiltonian::apply_block`: band blocking of the projector products (hypotheses 1, 2).
- `dft-numerics` `fused.rs` (OrderedFusedPlan, GridFusedPlan, FusedPlan alias) and `mkl_backend.rs`: the vendor pruned stick pipeline (hypothesis 3), lane staging (hypothesis 5).
- `dft-basis` `FftGridSpec`: grid choice is already the exact minimum; only a truncated-potential grid would shrink it (hypothesis 7). Coefficient order is by |k+G|; a stick-major internal order would make scatter and gather contiguous (minor; the vectors are permutation-invariant for every operation in the engine, but cube writers and the prefix-based cold start use the sorted order; hypothesis 8).
- Build configuration (hypothesis 4).
- `NonlocalOperator::new` and `dft-upf` radial.rs: radial table (hypothesis 6).

## Hypotheses for BAANDI

Ranked by (expected gain times confidence) over risk. Wall-time effects below are estimates for si8 at T=1 on dev08 (about 2,100 vectors per run, total 4.8 to 6.0 s), derived in section 3.

1. Band-blocked nonlocal traversal with unchanged per-band arithmetic order (bit-identical loop interchange).
   - Idea: process groups of g bands (g about 4 to 8) together inside each worker: for each projector column, read the column once and apply it to all g bands, running g independent accumulation chains side by side in the projection, and in the accumulation pass add the column times each band's weight into that band's output. Each band's sums keep exactly the same order of additions over coefficients and over projector columns, so results are bit-identical to now. The traversal blocks over BANDS (matrix reuse), not over output rows (that was P10J, ledger A43, a different axis).
   - Expected gain: removes both the L3 streaming (3.04 MB per band becomes about 3.04/g MB) and the latency-bound dependent chain (g independent chains). Estimate: nonlocal from about 0.2 ms to 0.05 to 0.08 ms per vector; saves roughly 0.3 s of 5 to 6 s (5 to 6 percent) at T=1, more at higher T where threads compete for the shared L3. On the Mac (matrix fits L2) the gain should be small; judge only on dev08.
   - Risk: low arithmetic risk (bit-identical by construction). Scheduling risk: apply_block currently gives workers single bands as stealable pieces (A48, A50); groups of bands reduce the piece count, so choose g from the band count and thread budget (for example g = min(4, ceil(m/T))) and keep the static piece layout deterministic.
   - Validation gate: existing `nonlocal_traversal_preserves_bits`-style bitwise tests extended to g in {1,2,4,8} and to odd tails; `scripts/bench_scf.py --require-identical` on gamma, k222s, k222; si8 and a different-projector-structure synthetic (0, 3 and 5 channels, skew and slab); dev08 profile with the 30-sample rule (ledger C), T = 1, 8, 16.
   - Conflicts: A43 (row-blocked traversal rejected on dev08): not the same change, but the proposer must cite it and show the matrix-reuse effect separately from row blocking; A48/A50 (piece granularity); A28 (band grouping in the FFT rejected: here the resource is different, the matrix not the potential).
2. Contiguous projector matrix and one matrix product per block for projection and accumulation (faer, or the MKL ZGEMM in the MKL build), as QE does. Variant of 1 with a different summation order, so not bit-identical.
   - Expected gain: about 0.2 ms to about 0.04 to 0.05 ms per vector (QE measures 42 microseconds on this shape): saves about 0.3 to 0.35 s (6 to 7 percent), and scales better with threads. Over hypothesis 1 the extra gain is small unless the library kernel is much faster than our interleaved loop: ADR 0019 measured MKL ZGEMM 2.5 to 4.2 times faster than faer on similar shapes.
   - Risk: Davidson trajectories change at rounding level (ledger A55, A49, A52 show SCF counts moving on toy cases); requires the architect's acceptance rule of A55 (energy within 1e-12 Ha, no converged case lost). The per-atom coupling stays block-diagonal (small products per atom); the packing rejection A38 concerns Rust GEMM operands, not a once-built matrix.
   - Validation gate: all 19 suite cases and the P14B acceptance table form; energies within 1e-12 Ha; compare with hypothesis 1 on dev08 before choosing.
   - Conflicts: none recorded; do after 1, only if 1 leaves a measurable gap to the matrix-product form.
3. Vendor pruned stick pipeline for the MKL build (batched 1D z transforms on sticks, y on active columns, x on planes, multiply fused per plane; descriptors owned by the plan, sequential threading layer) replacing the full-grid adapter. This is S-A of note 2, now with source-based numbers: QE with MKL pays the full 7.2 Mflop per band at 136 microseconds per transform, so a pruned pipeline at the same kernel efficiency would cost about 55 percent of that.
   - Expected gain: per vector FFT from about 0.3 to 0.4 ms down to 0.2 to 0.25 ms if the batched kernels reach 70 to 90 percent of the 3D kernel's rate (estimate; the fastqe report measured 3 to 5 times on the local step on another machine). Saves roughly 0.2 to 0.3 s (4 to 6 percent at T=1) and lowers per-vector cost below QE's 0.38 ms in total when combined with 1.
   - Risk: medium. Small strided batches inside the vendor library were 3 times slower with internal threading (keep threads at 1); descriptor creation about 21 microseconds each (create once); results differ at rounding level from the 3D adapter (normwise 1e-15, as the symmetric plane variant, ledger A27), so the same acceptance rule as 2; pure-Rust and MKL results already differ and are never required to be bit-identical across backends.
   - Validation gate: per-vector microbenchmark at 25^3, 36^3, a skewed and a slab-like box on dev08 before any SCF run; then the 19-case suite, energy within 1e-12 Ha, thread-determinism hashes across T = 1, 4, 8, 16.
   - Conflicts: A29 (plane pruning only up to about 60 percent active columns, no tuned threshold; keep that rule), A34 (threaded FFT rejected; keep it sequential), A30 (listed open); no conflict with A28.
4. Release and target configuration audit: ask what dev08 builds used; test `lto = "fat"`, `codegen-units = 1` and an x86-64-v3 (AVX2/FMA) target or run-time dispatch for the hand-written hot loops (nonlocal add, kinetic, density, scaling passes). The compiler does not contract multiply-add or reassociate sums, so outputs stay bit-identical for loops whose operation order is fixed.
   - Expected gain: unknown, 0 to 10 percent of the non-library part; direction supported by the observation that the hand-written loops and the library kernels diverge between Mac and dev08 (A43, A55). Do not claim a number before measuring.
   - Risk: portability of released binaries (a CPU feature requirement); handle by a separate "native" artifact or run-time dispatch, not by raising the default floor silently.
   - Validation gate: same binary comparison on dev08 with `--require-identical` on gamma, k222s, k222; profile before/after (30-sample rule); no tolerance change.
   - Conflicts: none; the question to the orchestrator is whether dev08 numbers in the relays were built with such flags.
5. Re-test lane staging and contiguous-batch lane transforms for the pure-Rust fused plan on dev08 only (not Mac), after counting how many cycles the gather/scatter of lanes takes in a profile of the local step. A11 measured 1 to 4 percent on the Mac, explicitly left dev08 and expensive-stride CPUs open.
   - Expected gain: 0 to 20 percent of the pure-Rust local step on dev08 (estimate from the lane-copy count in section 4; unmeasured); affects only the pure build, where MKL is 2.8 times faster on full transforms, so the benefit competes with hypothesis 3 for relevance.
   - Risk: low if bit-identical staging only; a batched lane kernel of our own would be a hand-written FFT and falls under the library policy (ADR 0003): do not write one without a decision.
   - Validation gate: bit-identical outputs; dev08 per-vector microbenchmark; no change to the strict bit gates.
   - Conflicts: A11 (rejected on the Mac; its own reconsideration clause: only if FFT is dominant again or strided access is much more costly, which dev08 may satisfy); A34 (no threads in lanes).
6. Radial projector table with cached interpolation (QE's idea) or, bit-compatible with the current quadrature, per-shell caching of radial transforms inside one k (equal |k+G| values share one quadrature).
   - Expected gain: setup only. A direct estimate: about 3 to 4 million Bessel evaluations per k for si8-like cases (2,969 plane waves, 2 radial functions, a mesh of several hundred points) which is of order 0.05 to 0.1 s per k; relevant only when the number of k points or the mesh is large (k444s has 32 k points). Measure `NonlocalOperator::new` first; adopt only if it exceeds a few percent of wall time at T=1.
   - Risk: a four-point Lagrange table at step 0.01 has relative error of order 1e-8 to 1e-9, which exceeds the 1e-12 Ha gate; a finer table or a higher-order interpolant is needed to stay within the gate. Per-shell caching is exact but gains only for symmetric k.
   - Validation gate: operator comparison against the current quadrature at the 1e-14 relative level for the exact variant; SCF energy within 1e-12 Ha for any interpolated variant.
   - Conflicts: none recorded.
7. (Exploratory, accuracy-changing) Truncated-potential wavefunction box (K < 2m) for early SCF iterations only, with the final certificate and the last iterations on the exact box. A box of 3m+1 points per axis has about 3 times fewer points than 4m+1 for si8 (25^3 against 36^3).
   - Expected gain: at most 2 to 3 times on the local step for iterations whose eigen-tolerance is loose (early SCF); nothing at convergence. The Davidson eigenvectors of the truncated operator differ from the exact ones by the truncation error, which bounds usable early thresholds to about the truncation error (unknown; to be measured per system, depends on the pseudopotential hardness).
   - Risk: high; violates the equivalence rules; an SCF with changing H between iterations changes the convergence path; the generality rule forbids adoption from silicon alone.
   - Validation gate: measure the truncation error of the local operator on the suite (hard and soft synthetic pseudopotentials, skewed and slab cells); adopt only if the measured error is below the loosest threshold in use with a margin and the SCF count does not rise on any suite case.
   - Conflicts: A21 (looser early eigenvectors raised SCF counts on several systems): this idea is of the same family and likely to meet the same failure; low priority.
8. (Minor) Stick-major internal ordering of coefficient vectors so that scatter and gather are runs of contiguous copies and the first transform pass reads the coefficient vector directly. Gain at most a few microseconds per vector out of about 300 (estimate); risk: touches ordering assumptions (cold start by lowest kinetic energy, output writers, tests). Do not start before 1, 3 and 5 are decided.

Order of work suggested: 4 (cheap audit, informs 1 and 5), 1, then 3 in parallel (MKL build only), then decide 2 from the remaining gap, 5 and 6 only on profile evidence; 7 and 8 last or never. Combined expected effect on si8 at T=1 on dev08, all estimates: about 10 to 13 percent of wall time from 1 plus 3, which would put the H application per vector at or slightly below QE's 0.38 ms; the larger factor (vector count, 2.2 times) and the algebra around H are outside this note.
