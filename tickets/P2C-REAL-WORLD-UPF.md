TASK_ID: P2C-REAL-WORLD-UPF
GOAL: Make the UPF reader accept real-world UPF v2 files written by common generators, which differ from the strict reading of the specification in two ways that the P2A synthetic fixtures did not cover. A real norm-conserving file (not available to you, on purpose) was rejected by `dft-cli inspect-upf` at two points; a diagnostic run in a throwaway tree showed that these two changes are enough for the file to be read and for its header values to match independent reports. Implement them properly with tests and documentation.
OWNED_FILES: crates/dft-upf/** (parser and its tests/fixtures), docs/upf-support.md. Do not touch other crates, manifests, ADRs, AGENTS.md or workspace files.
READ_ONLY_CONTEXT: AGENTS.md, crates/dft-upf/AGENTS.md, crates/dft-upf/src/parser.rs, crates/dft-upf/tests (fixture generator in tests/common), docs/upf-support.md, docs/decisions/0008, and the vendored upf crate sources in ../rust-dft-wt/rust-dft-vendor/upf/src (how numeric arrays and the `relativistic` attribute are decoded).
OBSERVED PROBLEMS (from the real file; you do not have it and must not ask for it):
1. The header contains `relativistic="no"`. The specification text lists "scalar | full | nonrelativistic", but real files written by older generators use "no". The parser currently accepts only "scalar" and "nonrelativistic" and fails with `unsupported feature: relativistic=no`. Required: accept "no" as a synonym of nonrelativistic (and keep "nonrelativistic" and "scalar"); keep rejecting "full"/fully relativistic and any other value with an explicit error that names the value. Record the discrepancy between the specification and real files in docs/upf-support.md.
2. Numeric arrays (PP_R, PP_RAB, PP_LOCAL, PP_BETA.*, PP_DIJ, PP_CHI.*, PP_RHOATOM) in real files are written several values per line (the section tag carries a `columns` attribute, for example columns="4"), with numbers separated by SPACES within a line and by NEWLINES between lines. The upf crate's decoder only splits on spaces: a value at the end of a line and the first value of the next line arrive as one token such as `1.410152633680000e-3\n1.445850817560000e-3`, and the decode fails with `invalid type: string ..., expected f64`. Required: make the reader robust to arbitrary ASCII whitespace (spaces, tabs, newlines, carriage returns, runs of them) between numbers. The diagnostic change that worked was to replace newlines by spaces in the text handed to the upf crate; implement the robust version of that idea (for example normalize every ASCII whitespace character to a single space before handing the text over, but be careful not to alter anything that is not whitespace, and keep line/position information in error messages usable or document that it is lost). Windows line endings must work too. State in the docs why this is safe for the supported subset.
TESTS (stated tolerances, no real UPF):
a. Extend the synthetic fixture generator (tests/common) with options: `relativistic="no"`, arrays wrapped four values per line with a `columns="4"` attribute on the sections, an array whose last line has fewer than four values, CRLF line endings, tabs and double spaces between numbers, and a mixture. Parse each variant and check that all numeric fields equal the same values as the unwrapped fixture bit for bit (the numbers are the same text, so equality must be exact).
b. Negative tests: relativistic="full" and an invented value ("foo") fail with the specific error naming the value; the previous negative tests (PAW, ultrasoft, spin-orbit, core correction, non-monotonic mesh, mismatched lengths, NaN, missing sections, truncated file) still produce the same errors.
c. `dft-cli inspect-upf` integration test on a wrapped, "no"-relativistic synthetic file prints SUPPORTED.
d. The radial-math tests of P2A are unchanged and still pass.
