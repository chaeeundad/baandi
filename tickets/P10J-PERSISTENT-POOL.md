TASK_ID: P10J-PERSISTENT-POOL
GOAL: Fix the two defects the dev08 measurement of P10I (commit 494bece, 2026-11-04) exposed: (1) si8 (8 atoms, one k point) gets slower with more threads: pure Rust T=1/4/8/16 wall 6.89/6.20/7.61/10.15 s (speedup 1.00/1.11/0.91/0.68), MKL 9.52/6.50/6.77/7.51 s; target is at least 3x at T=8; (2) the MKL build regressed on all 20 case/thread combinations versus fe0492b (old/new 0.83 to 0.92; si8 MKL T=1 from 6.334 s to 9.518 s, 1.50x slower).
EVIDENCE (from dev08, eu-stack samples, si8 pure T=8): 10 of 22 samples have the main thread inside `tiled::run` -> `std::thread::scope` -> `pthread_clockjoin` -> futex; at T=16, 12 of 29 samples show one thread only, the others between 2 and 16: threads are created and joined on EVERY GEMM call (the P10I `linalg/tiled.rs` uses std::thread::scope per call). Creation and join cost grows with T and exceeds the work of a single-k-point GEMM. Phase times: only diagonalization grows after T=4 (pure 5.36 s at T=4, 6.75 at T=8, 9.23 at T=16); density, mixing, potential stay flat. Mac (12 cores, aarch64) showed si8 2.0x at T=8, so the cost is platform dependent (thread creation on the dev08 kernel and 80 hardware threads with taskset to one socket).
OWNED_FILES: crates/dft-numerics/src (linalg.rs, linalg/tiled.rs, any new pool module, fused/mkl adapters only as needed), crates/dft-solvers/src and crates/dft-physics/src only to pass a pool/context handle, crates/dft-engine/src/scf.rs (thread budget and pool ownership only), docs/performance/optimization-log.md, docs/performance/README.md, docs/dependencies.md (only if a crate is adopted)
DESIGN REQUIREMENTS:
1. Persistent workers: no thread creation or join per GEMM or per band batch. One pool per SCF run (or per thread budget) created once and reused for every phase (GEMM tiles, projection, H|psi> band batches). Options: rayon (already in the lock file through other crates; license MIT or Apache-2.0) with an owned ThreadPool built from the thread budget, or a small std-only pool with condvar. Pick one, justify in the log, record in docs/dependencies.md if rayon becomes a direct dependency.
2. Determinism contract unchanged: the decomposition into tiles and the reduction order are fixed and independent of the thread count (same results at T=1,2,4,8,16 within one backend, bit for bit). Execution may be serial or parallel for the same decomposition.
3. Granularity: do not dispatch to the pool below a work threshold (flops per call) that is independent of the thread count; measure the threshold on the Mac and show a plot or table of time versus size. Small GEMMs run inline on the calling thread.
4. MKL feature path: the tiled/threaded code must not make MKL slower. At T=1 the MKL build must be at least as fast as fe0492b for every protocol case (old/new at least 0.98), and the dev08 si8 MKL T=1 time must return to about 6.3 s. Find out why MKL regressed (suspects: many small tile-sized `cblas_zgemm` calls instead of one large call, extra copies into tile buffers, the blocked projection replacing a faster path, per-call allocation, the keep-anchor read in gemm); fix by using large tiles for the MKL backend or one MKL call per logical GEMM, keeping the fixed-decomposition determinism. You cannot run MKL on the Mac: type-check with `cargo check --features mkl` and say what is unverified; the remote session will measure.
5. Single-thread cost: P10I made pure T=1 about 6 percent slower on the Mac for some cases while si8 T=1 got 1.42x faster on dev08; do not make T=1 slower than the P10I state.
